Pivot Table Generator

Use this free pivot table generator to turn a CSV or XLSX file into a readable summary. The tool processes your spreadsheet in the browser, so you can group, calculate, inspect, and export data without creating an account.

Turn rows of data into a useful summary

A good pivot table starts with a tidy source: a single header row, unique column names, and one record per row. Select a field for rows, an optional field for columns, and a value to calculate. Sum is useful for totals, Average shows a typical value, and Count shows the number of matching records.

For a sales report, you might group rows by Region, split columns by Category, and sum Sales. Review the finished table before exporting it or making a chart, especially when filters, blank values, or date fields are involved.

Prepare data the generator can check

A pivot table is only as dependable as the records behind it. Start with a rectangular range: one header row, a separate column for every property, and one observation on every following row. A transaction export might use Order Date, Region, Product, Sales, and Quantity. Remove report titles, merged cells, blank separator rows, and manually calculated subtotal rows before uploading. Those layout elements are useful in a finished report, but a pivot generator can mistake them for ordinary data.

Open the data preview after upload and inspect a few headers and values before choosing fields. Amounts and quantities should be recognized as numbers; dates should use a consistent format. If a value such as $1,200 is being treated as text, correct its source format or adjust the detected type before calculating. This short preparation step prevents common problems such as an unexpectedly low total, a blank group, or a single category called “Total.”

Choose fields to answer one clear question

Frame the question before configuring the table. For “Which region produced the most sales?” use Region in Rows, Sales in Values, and Sum as the calculation. For “How many orders did each team receive?” use Team in Rows and Count of an order field. Add a column field only when a second comparison helps, such as Category within each Region. Too many fields can make an otherwise correct table harder to read.

Filters should narrow a stated question, not hide inconvenient data. A filter for one year or product line can make a report useful, but record the time period and check the remaining row count. When you compare two exports, use the same field definitions and aggregation in both. That way a change in the result is more likely to reflect the data rather than a changed setup.

Verify totals before creating a chart

Use the pivot table as the evidence behind the visual. Compare a few cells with the source records, then check the grand total against a known total from the original spreadsheet. If the result seems wrong, inspect whether pre-calculated totals were included, duplicate rows exist, a filter is active, or the selected calculation is appropriate. Sum answers a total question, Count answers a record question, and Average answers a typical-value question; substituting one for another changes the meaning of the table.

After the table is correct, create a chart that fits the comparison. Bar charts are usually best for categories and rankings, line charts are best for a meaningful time sequence, and pie charts work only for a small number of parts of one whole. Export the checked pivot table as CSV or XLSX for review, or export the chart as PNG for a slide. Keeping the table with the chart makes the conclusion easier for another person to verify.

Worked example: support tickets by priority

Suppose a source file contains Ticket ID, Created Date, Team, Priority, and Resolution Hours. To compare workload by priority, put Priority in rows, Ticket ID in values, and choose Count. Verify that Ticket ID is unique and that blank priorities have been reviewed rather than silently excluded. Then compare one priority count with filtered source rows and confirm that the grand total equals the number of included tickets.

If the question changes to service speed, keep Priority in rows but use Average of Resolution Hours. The table now describes a typical resolution time rather than volume. Report the time period, state whether unresolved tickets are excluded, and be cautious when a category contains only a few records. A large average based on two unusual tickets should not be presented with the same confidence as an average based on hundreds.

This example shows why the field configuration belongs with the conclusion. “High priority has the largest count” and “High priority has the longest average resolution” are different findings produced from the same file. Preserve the row count, aggregation, filters, and summarized table so another person can reproduce the result.
